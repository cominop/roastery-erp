## Spec Reference (Section 6)
From `Roastery ERP - SPEC - Audit Trail.md`, section 6:

### 6.1 Single Change Undo
```python
def undo_audit_entry(audit_id):
    entry = AuditLog.query.get(audit_id)
    if entry.action == 'UPDATE':
        # Restore old_values
        update_record(entry.table_name, entry.record_id, entry.old_values)
        # Log the undo
        audit_log(action='UNDO', note=f'Reverted audit #{audit_id}')
    elif entry.action == 'DELETE':
        # Re-insert the deleted record
        insert_record(entry.table_name, entry.old_values)
```

### 6.2 Point-in-Time Revert
```python
def revert_to_timestamp(table_name, record_id, timestamp):
    entry = AuditLog.query.filter(
        table_name=table_name,
        record_id=record_id,
        changed_at <= timestamp,
        action != 'DELETE'
    ).order_by(AuditLog.changed_at.desc()).first()

    if entry:
        # Apply the new_values from that point
        update_record(table_name, record_id, entry.new_values)
```

## What to Build

### Server-side (Express routes in server/index.cjs)

**1. POST /api/audit-log/:id/undo — Undo a single change**
- Look up the audit entry from `shared.audit_log`
- If action == 'UPDATE': restore `old_values` back to the record in `db_fcc_erp` schema via UPDATE SQL
- If action == 'DELETE': re-insert using `old_values` via INSERT SQL
- If action == 'INSERT': delete the record (inverse of insert — but ONLY if no subsequent changes exist for this record)
- Create an `UNDO` audit log entry recording what was done
- Return: `{ success: true, message: "Change undone", new_audit_id: ... }`

**2. POST /api/audit-log/:table/:record_id/revert — Point-in-time revert**
- Accept body: `{ timestamp: "2026-07-28T10:00:00Z" }`
- Find the most recent audit entry BEFORE that timestamp (action != 'DELETE'), ordered by changed_at DESC
- Apply that entry's `new_values` to the record via UPDATE SQL
- Create an audit entry for the revert
- Return: `{ success: true, message: "Reverted to point-in-time", new_audit_id: ... }`

**Important server-side considerations:**
- The `audit_log` is in the `shared` schema: `shared.audit_log`
- The ERP tables are in the `db_fcc_erp` schema: `db_fcc_erp.<table_name>`
- Check that the record still exists before undoing a DELETE (it may have been deleted again)
- For point-in-time revert: skip entries where `new_values` is null
- Log the undo/revert as a new audit entry with action='UNDO' and note field recording what was done
- Get current user info from request (already set by middleware: req.user)
- IMPORTANT: The existing audit trigger will fire on the data modification, creating a new audit entry. This is expected — the UNDO entry we manually insert is separate.
