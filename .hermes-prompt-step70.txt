# Step 70: Visual Editor 0 — Data model & types

## Context
You are working on the Roastery ERP project at `/home/fcc-student/Desktop/_DEV/roastery-ui/`. The codebase is a React + Express + PostgreSQL ERP system.

The existing form system reads legacy Access form definitions from `shared.objects` and renders them via `FormRenderer`. These forms are read-only artifacts from the Access migration — they cannot be edited through the UI.

This step introduces the **foundation for a visual drag-and-drop form editor** that will let users design forms directly in the browser. This is Step 0 of the Visual Editor feature, establishing the data model, TypeScript types, database schema, and API endpoints. No UI is built yet.

## What was built

### 1. TypeScript types — `src/visual-editor/types.ts`

The full data model for the visual editor, including:

- **`VisualEditorControl`** — the core control definition. Has all properties needed for a form builder: position (`left`, `top`, `width`, `height`), style (`VisualStyle`), data binding (`DataBinding`), validation (`Validation`), event bindings (`EventBindings`), editor flags (`locked`, `visible`, `enabled`), and type-specific properties (tab pages, subform links, image settings, etc.). Each control has a unique `id` (UUID) for React keys and drag/drop tracking.

- **`VisualEditorControlType`** — union of 16 supported control types: `text-box`, `label`, `command-button`, `combo-box`, `check-box`, `option-button`, `toggle-button`, `tab-control`, `page`, `subform`, `image`, `line`, `rectangle`, `list-box`, `option-group`, `attachment`.

- **`VisualEditorSection`** — a form section (header/detail/footer) with visibility, height, background color, and controls array.

- **`VisualEditorForm`** — the full form definition: name, caption, record source, permissions (allowEdits, allowAdditions, allowDeletions), navigation buttons, modal/popup flags, filter, order by, three sections, editor canvas settings, events, module code, and optimistic concurrency `version`.

- **`EditorGridSettings`** — canvas configuration: grid size, snap-to-grid, show grid, grid color.

- **`ToolboxItem`** — palette entries for the drag-and-drop toolbox, organized by category (`input`, `display`, `action`, `container`, `decoration`, `data`). Each item has a type, label, icon, and default size.

- **`TOOLBOX_ITEMS`** — a pre-built array of 15 toolbox items with sensible defaults.

- **`VisualEditorClipboard`** — clipboard data for copy/paste of controls.

- **`EditorSelectionState`** — editor UI state: selected IDs, active section, mode (select/pan/insert), zoom level.

- **API request/response types** — `VisualFormListItem`, `VisualFormCreateRequest`, `VisualFormUpdateRequest`.

### 2. Database migration — `server/sql/step-70-visual-editor.sql`

Creates the `shared.visual_forms` table with:

- **Columns**: `id`, `name` (unique per company), `caption`, `record_source`, `allow_edits`, `allow_additions`, `allow_deletions`, `navigation_buttons`, `modal`, `popup`, `filter`, `order_by`, `sections` (JSONB), `editor_settings` (JSONB), `events` (JSONB), `module`, `version` (optimistic lock), `company_id`, `created_by`, `updated_by`, `created_at`, `updated_at`.

- **Indexes**: unique index on `(company_id, name)`, updated_at index for listing.

- **Triggers**: auto-updates `updated_at` on row modification.

- **Helper functions**:
  - `fn_visual_forms(p_company_id)` — returns form metadata list (camelCase-ready)
  - `fn_get_visual_form(p_name, p_company_id)` — returns full form definition as JSONB with camelCase keys
  - `fn_save_visual_form(...)` — upsert with optimistic concurrency control (version check on update, auto-increment)
  - `fn_delete_visual_form(p_name, p_company_id)` — delete by name

### 3. API routes — `server/index.cjs`

Five RESTful endpoints:

- **`GET /api/visual-forms`** — list all visual form definitions (metadata only, no sections)
- **`GET /api/visual-forms/:name`** — get full form definition with sections, controls, editor settings
- **`POST /api/visual-forms`** — create a new form with default empty sections (header/detail/footer)
- **`PUT /api/visual-forms/:name`** — update a form definition (requires `version` for optimistic lock; returns 409 on conflict)
- **`DELETE /api/visual-forms/:name`** — delete a form (returns 404 if not found)

### 4. Barrel export — `src/visual-editor/index.ts`

Re-exports all types and the `TOOLBOX_ITEMS` constant so consumers can import from `@/visual-editor`.

## Key design decisions

- **Separate from legacy forms**: Visual editor forms live in their own table (`shared.visual_forms`), not in `shared.objects`. This avoids polluting the Access import data and allows the editor to have its own schema.

- **JSONB sections**: The form layout (header, detail, footer) is stored as a single JSONB column rather than normalized into control/section tables. This gives us schema flexibility (controls can have arbitrary type-specific properties) and avoids complex joins. The trade-off is that we can't query individual controls via SQL — but we don't need to.

- **Optimistic concurrency**: The `version` column is incremented on every save. The PUT endpoint rejects stale updates with a 409 so users don't overwrite each other's changes.

- **CamelCase API**: The `fn_get_visual_form` function returns camelCase keys so the frontend can use the JSONB directly without manual conversion.
