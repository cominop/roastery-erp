## Important notes
- The events are stored in `VisualEditorForm.events` (EventBindings object) — each event name matches a key in EventBindings (e.g., 'onClick' maps to some property)
- The VisualEditorForm type uses camelCase event names in EventBindings (onClick, onDblClick, etc.) but the VBA form events use snake_case (on_before_open). Map between them — on_before_open maps to a specific field in EventBindings, or if no direct mapping exists, store custom events in a custom property
- Actually, looking at the types more carefully: The existing EventBindings interface uses Access-style camelCase (onClick, onDblClick, onBeforeUpdate, onAfterUpdate, onChange, onEnter, onExit, onGotFocus, onLostFocus, onKeyDown, onKeyUp, onKeyPress). The VBA form events (on_before_open, on_after_open, etc.) don't have a direct mapping in the current EventBindings type.
- For form-level events described in Appendix A, store them in a new field on VisualEditorForm called `formEvents` (a Record<string, string> mapping event name → handler script), or store them inside the existing `events` field by extending the type. Choose the simplest approach: add a `formEvents?: Record<string, string>` field to the form definition concept that the EventBindingPanel manages. The onChange callback will return the form with this field populated.
- Do NOT modify types.ts directly — the component should work with the existing type system. Use the `form.module` field for the form module script, and for the VBA form events (on_before_open etc.), use a separate concept: store them in the VisualEditorForm's existing `events` field using snake_case keys (on_before_open, on_after_open) since TypeScript's index signature allows extra keys on the EventBindings object.
- To be safe: check if EventBindings has [key: string]: string | undefined via its structural typing. If not, just use a separate field approach.
- Style should match the existing visual-editor components (small fonts, subtle borders, muted colors).
