```sql

  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  table_name      VARCHAR(255) NOT NULL,
  record_id       INTEGER NOT NULL,
```

6. Drop `audit_log_old` after migration

IMPORTANT: PostgreSQL partitioning requires that the partition key column is included in the primary key or the primary key is dropped. Since we partition BY RANGE (changed_at), change the approach:
- Drop the existing PRIMARY KEY on `id`
- Keep `id` as a column (UUID, NOT NULL, DEFAULT gen_random_uuid()) but without PK constraint
- Use `id` as a UNIQUE index instead (with included changed_at for partition compatibility)  
- Or better: make the primary key (id, changed_at) composite to satisfy the partition requirement

### 2. GIN indexes

Add GIN indexes for JSONB columns to enable fast JSON path queries:

```sql
CREATE INDEX IF NOT EXISTS idx_audit_log_old_data_gin
  ON shared.audit_log USING GIN (old_data jsonb_path_ops);

CREATE INDEX IF NOT EXISTS idx_audit_log_new_data_gin
  ON shared.audit_log USING GIN (new_data jsonb_path_ops);
```

These indexes enable queries like:
```sql
-- Find all changes where a specific field was modified
SELECT * FROM shared.audit_log 
WHERE new_data @> '{"status": "shipped"}'::jsonb;

-- Find entries where productname changed
SELECT * FROM shared.audit_log 
WHERE old_data->>'productname' != new_data->>'productname';
```

### 3. Async write queue

Implement an async write mechanism that decouples audit logging from the main transaction. The trigger currently writes synchronously inside the same transaction — this means every INSERT/UPDATE/DELETE on any ERP table waits for the audit insert to complete.

**Option: pg_notify + listener pattern (recommended)**

1. Create an **audit queue table**: `shared.audit_queue` with columns:
   - id SERIAL PRIMARY KEY
   - payload JSONB (the full audit entry data serialized)
   - status VARCHAR(20) DEFAULT 'pending' (pending, processing, done, failed)
   - created_at TIMESTAMPTZ DEFAULT NOW()
   - processed_at TIMESTAMPTZ

2. Modify the trigger function `shared.audit_log_trigger()`:
   - Instead of INSERT INTO shared.audit_log directly, INSERT INTO shared.audit_queue (payload) with the audit data
   - Then do `PERFORM pg_notify('audit_queue_channel', queue_id::text)`

3. Create a **background worker function**: `shared.process_audit_queue()` that:
   - Reads pending entries from audit_queue (with FOR UPDATE SKIP LOCKED)
   - Inserts them into the partitioned shared.audit_log
   - Marks them as 'done' in audit_queue
   - Returns count of processed entries

4. Create a **PostgreSQL LISTEN/NOTIFY handler**: Create a stored procedure/function that listens on 'audit_queue_channel' and calls process_audit_queue() automatically.

5. Create a **node.js cron worker**: `/home/fcc-student/Desktop/_DEV/roastery-ui/server/cron/process-audit-queue.cjs` that:
   - Runs every 5 seconds via setInterval
   - Calls `SELECT * FROM shared.process_audit_queue()`
   - Handles backpressure (if queue is growing faster than processing, log a warning)

6. Register this cron in `server/index.cjs` at startup

**Fallback option (if pg_notify is complex with trigger):**
Use a simpler queue-based approach:
- Keep the trigger writing to `shared.audit_queue` (fast INSERT without heavy JSONB processing)
- The background worker reads from queue, processes JSONB, inserts into partitioned audit_log
- Run every 2-3 seconds
