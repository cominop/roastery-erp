## What to build

### 1. Expression Parser (`server/calculated-fields/expression_parser.py`)

Create a Python module at `server/calculated-fields/expression_parser.py` that implements a safe expression parser.

**Tokeniser** — Convert expression string to tokens:
- Parse field references: `{field_name}` — wraps in curly braces
- Parse string literals: `"hello"` or `'hello'`
- Parse number literals: `42`, `3.14`, `-5`
- Parse boolean literals: `true`, `false`
- Parse operators: `+`, `-`, `*`, `/`, `=`, `!=`, `>`, `<`, `>=`, `<=`, `AND`, `OR`, `NOT`
- Parse parentheses: `(`, `)`
- Parse commas: `,`
- Parse function names: `SUM`, `COUNT`, `AVG`, `IF`, `LOOKUP`, etc. (alphanumeric identifiers)
- Parse whitespace (skip)

**AST Builder** — Convert tokens to an AST:
- Expression types to support:
  - `FIELD_REF` — `{field_name}` (or `{table_name.field_name}`)
  - `LITERAL` — string, number, boolean
  - `BINARY_OP` — left op right (e.g., `{a} + {b}`)
  - `UNARY_OP` — op operand (e.g., `-{a}`, `NOT {b}`)
  - `FUNCTION_CALL` — name(args...)
  - `COMPARISON` — left op right (e.g., `{a} = 5`, `{b} > 10`)

**Operator precedence** (from highest to lowest):
1. Unary: `-`, `NOT`
2. Multiplicative: `*`, `/`
3. Additive: `+`, `-`
4. Comparison: `=`, `!=`, `>`, `<`, `>=`, `<=`
5. Logical: `AND`
6. Logical: `OR`

**Safe design**:
- No use of eval(), exec(), compile(), or __import__ anywhere
- Pure tokeniser + recursive descent parser
- The AST is a simple data structure (dicts with type/fields), not executable code
- Validation: reject invalid expressions with clear error messages (position + expected vs found)

### 2. AST Node Types (`server/calculated-fields/ast_types.py`)

Create a types module with dataclasses or TypedDicts for AST nodes:

```python
@dataclass
class FieldRef:
    type: Literal["FIELD_REF"]
    table: str | None      # Optional table qualifier
    field: str             # Field name

@dataclass
class Literal:
    type: Literal["LITERAL"]
    value: str | float | int | bool | None
    literal_type: str      # 'string', 'number', 'boolean', 'null'

@dataclass
class BinaryOp:
    type: Literal["BINARY_OP"]
    operator: str          # '+', '-', '*', '/'
    left: Expression
    right: Expression

@dataclass
class UnaryOp:
    type: Literal["UNARY_OP"]
    operator: str          # '-', 'NOT'
    operand: Expression

@dataclass
class FunctionCall:
    type: Literal["FUNCTION_CALL"]
    name: str              # 'SUM', 'COUNT', 'IF', etc.
    args: list[Expression]

@dataclass
class Comparison:
    type: Literal["COMPARISON"]
    operator: str          # '=', '!=', '>', '<', '>=', '<='
    left: Expression
    right: Expression

Expression = FieldRef | Literal | BinaryOp | UnaryOp | FunctionCall | Comparison
```

### 4. Error handling

Create `server/calculated-fields/parse_error.py`:
```python
class ParseError(Exception):
    def __init__(self, message: str, position: int, expression: str):
        self.message = message
        self.position = position
        self.expression = expression
        # Show the expression with a caret pointing to the error position
        # e.g.:
        #   {a} + {b} )
        #              ^
        #   Unexpected ')'
        super().__init__(self.__str__())

    def __str__(self):
        return f"{self.message} at position {self.position}\n{self.expression}\n{' ' * self.position}^"
```

### 5. Tests (`server/__tests__/expression_parser.test.py`)

Create comprehensive tests for the parser:

**Tokeniser tests**:
- Simple field reference: `{name}` → [FIELD_REF("name"), EOF]
- String literal: `"hello"` → [STRING("hello"), EOF]
- Number literal: `42`, `3.14` → [NUMBER(42), EOF], [NUMBER(3.14), EOF]
- Boolean: `true`, `false` → [BOOLEAN(True)], [BOOLEAN(False)]
- Mixed: `{first_name} + " " + {last_name}` → [FIELD_REF, PLUS, STRING, PLUS, FIELD_REF, EOF]
- Function call: `SUM({quantity} * {price})` → [IDENTIFIER("SUM"), LPAREN, FIELD_REF, STAR, FIELD_REF, RPAREN, EOF]
- Comparison: `{status} = 1` → [FIELD_REF, EQ, NUMBER(1), EOF]
- Logical: `{a} > 10 AND {b} < 5` → [FIELD_REF, GT, NUMBER(10), AND, FIELD_REF, LT, NUMBER(5), EOF]
- Unary: `-{amount}` → [MINUS, FIELD_REF, EOF]
- Null: `null` → [NULL, EOF]

**Parser tests** (AST construction):
- `{name}` → FieldRef(field="name")
- `{a} + {b}` → BinaryOp(operator="+", left=FieldRef(field="a"), right=FieldRef(field="b"))
- `{a} * {b} + {c}` → BinaryOp(operator="+", left=BinaryOp(operator="*", ...), right=FieldRef(field="c")) — precedence
- `({a} + {b}) * {c}` → BinaryOp(operator="*", left=BinaryOp(operator="+", ...), right=...) — parens
- `SUM({a}, {b})` → FunctionCall(name="SUM", args=[FieldRef(field="a"), FieldRef(field="b")])
- `{a} = 5` → Comparison(operator="=", left=FieldRef(field="a"), right=Literal(5))
- `-{amount}` → UnaryOp(operator="-", operand=FieldRef(field="amount"))
- `{a} > 10 AND {b} < 5` → BinaryOp(operator="AND", left=Comparison(...), right=Comparison(...))
- `IF({status} = 1, "Active", "Inactive")` → FunctionCall(name="IF", args=[Comparison, Literal, Literal])
- `{customers.name}` → FieldRef(table="customers", field="name") — dotted field ref

**Error tests**:
- Unclosed string: `"hello` → ParseError
- Unclosed field ref: `{name` → ParseError
- Mismatched parens: `({a} + {b}` → ParseError
- Invalid operator: `{a} %% {b}` → ParseError
- Empty expression: `` → ParseError
- Trailing operator: `{a} +` → ParseError

**Edge cases**:
- Spaces everywhere: `  {a}  +  {b}  ` → should parse correctly
- Nested function calls: `SUM(IF({a} > 0, {b}, 0), {c})`
- Table-qualified field: `{order_details.quantity}`
- Chained comparisons: `{a} > 5 AND {b} < 10 OR {c} = 0`
- Deeply nested: `((({a})))` → FieldRef
- Unicode field names: `{café}` → FieldRef(field="café")

## Important notes

- No eval(), exec(), compile(), __import__ — the parser is 100% safe by design
- Use Python 3.11+ features (dataclasses, type hints, Literal types)
- The parser uses recursive descent — clean, readable, maintainable
- Error messages MUST include the position and a caret pointing to the error location
- The parser should be a standalone module with no dependencies on the rest of the codebase
- The `{table_name.field_name}` syntax is important for cross-table references
- Field references use curly braces `{}` to distinguish them from identifiers
- Function names are bare identifiers (no braces): `SUM(...)`, `IF(...)`
- String literals use double quotes `"..."` or single quotes `'...'`
- Boolean literals: `true`, `false` (case-insensitive?)
- Null literal: `null`
- Numbers can be integers or floats, and negative numbers are handled via unary minus
